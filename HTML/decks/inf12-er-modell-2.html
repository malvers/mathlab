Warum der Fremdschlüssel auf der n-Seite steht

Eine Klasse hat viele Schüler, ein Schüler hat eine Klasse

In der Tabelle Schueler passt genau ein Klassenverweis in eine Zeile

Umgekehrt müsste in Klasse eine Liste von Schülern stehen — das geht in einer Spalte nicht

Eine Spalte enthält einen Wert. Das ist die erste Normalform, kommt in drei Wochen

Deshalb: eins steht bei viele, nicht viele bei eins

Warum n:m nicht direkt geht

Ein Schüler belegt viele Kurse, ein Kurs hat viele Schüler

In Schueler passt keine Kursliste, in Kurs keine Schülerliste

Also entsteht eine dritte Tabelle: Belegung

Sie enthält beide Fremdschlüssel — und beide zusammen sind der Primärschlüssel

Attribute der Beziehung — die Note — gehören genau dorthin

Nicht verzagen, Doc Alvers fragen!

Das Relationenschema als SQL

CREATE TABLE Schueler (
    snr INTEGER PRIMARY KEY, name TEXT, vorname TEXT, klasse TEXT);

CREATE TABLE Kurs (
    knr INTEGER PRIMARY KEY, bezeichnung TEXT, stunden INTEGER);

CREATE TABLE Belegung (
    snr  INTEGER REFERENCES Schueler(snr),
    knr  INTEGER REFERENCES Kurs(knr),
    note INTEGER,
    PRIMARY KEY (snr, knr)
);

Die Schreibweise für die Klausur

RelationSchema
SchuelerSchueler(snr, name, vorname, klasse)
KursKurs(knr, bezeichnung, stunden)
BelegungBelegung(snr, knr, note)

Primärschlüssel werden unterstrichen, Fremdschlüssel kursiv oder mit Pfeil markiert

In Belegung ist snr, knr zusammen Primärschlüssel und je einzeln Fremdschlüssel

Was beim Löschen passieren kann

RegelVerhalten beim Löschen eines Schülers
RESTRICT / NO ACTIONLöschen wird abgelehnt, solange Belegungen bestehen
CASCADEdie Belegungen werden mitgelöscht
SET NULLder Verweis wird auf NULL gesetzt

Die Voreinstellung ist meist RESTRICT — sicher, aber unbequem

CASCADE ist bequem und gefährlich: ein Löschbefehl räumt halbe Datenbestände ab

Fun Facts: Relationenmodell

Edgar F. Codd veröffentlichte das Relationenmodell 1970 bei IBM

Der Titel des Aufsatzes: „A Relational Model of Data for Large Shared Data Banks“

Codd formulierte später zwölf Regeln dafür, wann ein DBMS relational heißen darf

Kaum ein DBMS erfüllt alle zwölf — auch heute nicht

Der Begriff Relation meint die Tabelle, nicht die Beziehung — eine ewige Verwechslung
